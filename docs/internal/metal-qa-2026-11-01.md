- **Kit 11 brief.** Read in full from `https://airwallexdev.com/agentic-banking-builder-guide.md`, section 11, downloaded raw with curl. WebFetch returned only a summary.
- **Metal docs.** Read from `docs.metalntwx.com`: mandates, payouts, require-signed-order, clearing, x402, facilitator, metal-agent, receive policy, settlement, finality certificates, smart accounts, programmable compliance, and regulatory access.

Each ✅ below rests on three things:

  - consistency between the code, the ledger and the amounts.

  The project's own claim, "60 of 60 receipts succeeded", was not reproduced.

### The ❌ items

1. **The current code makes its own refusal look like Metal's (§4.1).**
   - `src/policy/holds.ts:79` refuses an over-cap purchase before anything is signed. It checks against the cap in Purser's audit log and returns the string `mandate_cap_exceeded: 0.04 is over the sourcing mandate's 0.03 a payment`. The refusal surfaces through `src/metal/pay.ts:40-47` (`onBeforePaymentCreation` abort).
   - Metal's facilitator never sees the 0.04 purchase. The run logs from dry-14 onward, the agents' messages ("so Metal refused #41") and the draaiboek ("Metal weigert") all credit Metal.
   - The recorded Friday run 1 predates this: audit row 91 holds the bare code `mandate_cap_exceeded`, which came from Metal. The next live run, which is meant to become the new recording, would not show it.
2. **The licence fee is wrongly placed on a Metal mandate (§5.2).** README line 36 says the licence fee "runs on its mandate". It is paid by Airwallex FX and SWIFT (`src/cli/licence.ts`) and touches no Metal mandate.
3. **A wrong source is cited (§5.1).** `docs/metal-award.md` §3 gives "F-tests (`runs/2026-10-29-f1.md`)" as proof that "a payment in doubt is looked up in `/settlements` by its nonce". That log covers an Airwallex approval that arrived too late. It never mentions `/settlements`.
4. **Dry-run logs credit Metal with refusals made by Purser's code (§5.5).** Examples: `docs/runs/2026-10-31-dry-17-18-agents.md:14,37,58` ("refused by the Metal mandate", "refused by Metal"), on code where `holds.ts:79` refuses first.

### The 🟠 items, in priority order

1. **Face ID is not on chain (§4.2).** The CFO's passkey approval sits off chain. The single owner key on the runner signs every bind and replace. The chain would accept a replace with no Face ID at all.
2. **Four eyes is not on Northwind's account (§4.3).** The 2-of-2 accounts (EOA keys on 30 and 31 Oct; passkeys on 1 Nov) are separate test accounts. Northwind's account has one owner on chain, so "both passkeys for every mandate change" is a rule in Purser's app only.
3. **The passkey owners are stand-ins (§2.17, §4.4).** The passkeys are software stand-ins (`docs/runs/passkey-owners.json`: "not a phone") or Chrome virtual authenticators (dry-93, no hashes recorded). No real phone has signed on chain yet, and the relay Worker has not been redeployed with this change.
4. **"Refused on chain" has no transaction behind it (§2.9, §4.5).** In the recorded run, the 0.04-over-0.03 refusal and the `mandate_revoked` refusal exist only as audit or log lines. Recorded on-chain refusals do exist in the four-eyes world, `0xda8acb12…a6b8` (`mandate_cap_exceeded`) and `0xf97bcade…f98d` (revoked), but no document links them.
5. **Finality certificates are reported, not proven (§2.15).** The BLS signature is not verified. The recorded run's certificates expired. The 26 stored certificates come from test worlds.
6. **The licence fee has not been paid in a recorded live run (§1.7, §1.16).** Only dry runs paid it, with virtual passkeys and no ids in the logs.
7. **The purchase-timeout path has never run live (§1.34, §2.11).** The `/settlements` nonce lookup is covered by tests only, yet requirements-matrix K7e says ✅.
8. **The recorded Northwind world shows only part of the Metal story (§4.7).** Clearing, the receive policy, four eyes, compliance, finality certificates and passkey owners each ran in a separate world.
9. **The README overclaims in two places (§5.3, §5.6).**
   - "An agent's mandate changes only when the CFO signs … with Face ID": the owner key could change it at any time.
   - "With the agents on, its own split, e.g. 14 / 2 / 4": this happened only in dry runs, against the project's own rule in claims.md.
10. **Clearing receipts are labelled before they are final (§4.10).** They are `preconfirmed`, and the code never watches `Clearing.finalizedCount` before calling an epoch final.
11. **The owner signer runs in the same process as the Claude agents (§4.11)** when `KIT11_AGENTS=on`.
