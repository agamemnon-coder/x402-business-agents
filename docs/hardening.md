going public. Each finding gets a row; a row is closed only with a commit and a test. Code that moves money is not
changed before the Friday runs: those fixes land after run 2.

## Findings

| # | Finding | Severity | Status |
|---|---|---|---|
| HF1 | The relay rate-limits what the phone sends, but not failed viewer-key attempts on `/api/*` or webhooks with a bad signature: they are refused, not counted. The viewer key is 128 bits, so guessing is not practical; counting them stops floods and makes guessing visible. | low | fixed on `build/next` (deployed after the runs): 20 failed attempts per address in ten minutes, then 429 before the key or signature is checked; the runner's own route is not counted (`test/relay-worker.test.ts`) |
| HF2 | JSON answers from the relay carry `nosniff`, `no-store` and `no-referrer`, but not HSTS; the HTML pages do. workers.dev is HTTPS-only, so this is defence in depth. | info | fixed on `build/next` (deployed after the runs): HSTS is a common header on every answer |
| HF3 | The pre-commit secret scan did not include the Airwallex webhook secrets (they live in the keys repo, not in the environment). | low | fixed: the scan now reads them from the keys dirs; full history is clean |
| HF4 | `docs/airwallex.md`'s scoped-key table missed `GET /fx/rates/current` and `POST /beneficiaries/schema`, added this week. | info | fixed |
| HF5 | ESLint: 15 findings. Fixed now: the injection scanner's invisible characters are written as `\u` escapes (proved identical over all 65,536 BMP characters), and unused imports in the red team CLI and a browser check. Left for after the runs: unused assignments in `src/approve/client.ts`, `src/passkey/process.ts`, `src/servers/approvals.ts`, and errors without a `cause` in `src/policy/cards.ts`. | info | fixed on `build/next`: the last 10 findings fixed (unused assignments removed, errors carry their `cause`); `npm run lint` runs in CI |
| HF6 | `netEarnings` (`src/agents/sweep.ts:33-34`) counts only PAID and HELD sweeps and refunds as gone. A pull still PENDING (sent, may still settle) is counted as unswept earnings, so planning a new sweep could plan it again. Today `npm run s3` resumes the unfinished sweep first, and the treasury mandate's budget is a limit on chain, so no money moved twice. | medium | fixed before the Friday runs: PENDING refunds and sweeps now count as gone (`test/sweep.test.ts`); the only caller already resumed an unfinished sweep, so no double sweep was possible, but a PENDING refund could have made the planned sweep too large |
| HF7 | Policy from plain words: a quote is checked as a plain substring and its amount is read from the quote alone, so a quote can cut a number. With "at most €1500 a month", a draft quoting "0" for `approval.refund_each` (0.10 → 0.00) is kept. The CFO still signs the one proposal, but the rule "the model may not split amounts" does not hold (`src/policy/fromText.ts:83, :92`). | medium | fixed on `build/next`: the amount must appear as a whole number both in the quote and in the CFO's text; property un-skipped |
| HF8 | A correctly signed but malformed card event is recorded as an approved charge: `transaction_amount` true, null, [45], "0x2d", "1e2" or "" and any `process_result` are read with `Number()` and accepted (`src/policy/cardHooks.ts:39`, `src/airwallex/issuing.ts:128, :134`). It needs the webhook secret, so it is a misreading, not a forgery; it also counts toward velocity. | medium | fixed on `build/next`: unknown statuses, non-string ids, a bad currency or date and any amount that is not a plain decimal number throw, so the event is not recorded; property un-skipped |
| HF9 | The runner's webhook handler can throw on a signed body (`null`, or a `name` like `{"toString":""}`), though its comment says it never does (`src/policy/cardHooks.ts:31, :35`). The relay only forwards JSON objects. | low | fixed on `build/next`: a parsed body that is not an object with a string `name` is ignored, never thrown on; properties un-skipped |
| HF10 | The relay checks a body that is not JSON against an empty string (`worker/src/core.ts:327`): wrong status codes (400 for 401 and back), nothing kept either way. | low | fixed on `build/next`: the signature is checked over the raw text first (401), then the body is parsed (400 "malformed event") |
| HF11 | The pay guard reads base units with `Number()` (`src/metal/pay.ts:42`) and can round down above 2^53 × 10^16 base units: no practical effect, every cap refuses such an amount. | info | fixed on `build/next`: an offer over 2^53 cents is refused before the guard and before signing; property un-skipped and run over the full range |
| HF12 | Card transactions with the same card, amount, outcome and timestamp are treated as one (`src/policy/cards.ts:205-207`), for Airwallex's two ids per authorisation. Two identical charges in the same instant would count once. Check how precise Airwallex's timestamps are. | low | checked, accepted: Airwallex's sandbox gives milliseconds (rehearsal 6: `21:38:28.947Z`, `21:38:34.307Z`), and Purser's client makes at most one Airwallex call per 200 ms, so one agent cannot make two identical charges in the same millisecond through Purser; the transaction id still decides first |

## Fresh security review of `build/next` (30 October)

An independent review of everything added this round (Ask Purser, B1 quarantine, the Lab, the relay changes). Every
finding is fixed with a test in `test/review-oct30.test.ts` and, where an attacker is involved, a red team attack.

| # | Finding | Severity | Status |
|---|---|---|---|
| R1 | A chat message through the relay was answered with `rail` set and no asker, so it took the "within the CFO policy" path: anyone with the viewer link (or a relay inserting `ask` items) could get task cards up to 300.00 each with no Face ID. The reviewer reproduced three ACTIVE 290.00 cards from three POSTs. The phone's text "nothing is issued before you approve it with Face ID" was not true. | high | fixed: only the CFO typing at the runner (`npm run ask`, `from: "runner"`) can get a card within the policy. The relay uses `relayAsk`, which never has Airwallex and always proposes. Within the policy also needs: the amount at or under the four-eyes threshold, fewer than 3 such cards in 24 hours, the amount written next to € or EUR, and the date written in the message. Red team `ask-viewer-link-card` |
| R2 | Floods of proposals: each held payment from a stranger made two proposals (dust and repeats too); an outside agent could ask for task cards without limit; a large pending set could push the relay state past its 1.5 MB limit and hide the emergency stop. | medium | fixed: dust (under 0.01) is held and shown but gets no proposals, and a sender gets one pair of options at a time; an outside agent has one waiting request and five asks an hour; the dashboard link has three waiting requests; the relay gets at most 50 proposals, policy changes (the stop among them) first. Red team `ask-agent-flood`, `quarantine-dust-flood` |
| R3 | The phone said "Purser read this from your own message" for every task card, also when an outside agent or a viewer asked; the dashboard labelled every chat line "You". | medium | fixed: `asked_by` is in the signed terms (`cfo-at-runner`, `dashboard-link` or the agent's id); the phone shows "Asked by" and a warning that fits; the dashboard labels lines "You", "Dashboard link" or "Agent ext:…" |
| R4 | Any number in the message passed the "amount in the message" check, so a misread room number could become a card within the policy. | low | fixed: within the policy the amount must sit next to € or EUR and a read date must be in the message; otherwise it is a proposal, where the CFO sees what was read |
| R5 | Task-card numbers came from `COUNT(*)` and the row was written after Airwallex answered: a race or a crash could reuse a number or leave a live card the emergency stop did not know; a runner restart could answer a queued ask twice. | low | fixed: the row is reserved (PENDING) with the next number in one write before Airwallex is asked; a reservation unfinished after two minutes has its card frozen and is marked FAILED by the runner's card tick; a relay ticket is answered once |
| R6 | Accepting a held payment never checked the destination against the sweep wallet, and the phone did not show the address. | low | fixed: an accept to any address but the sweep wallet is refused before Metal is asked; the phone shows the full address for return and accept |
