# Run log: four eyes on chain (30 October 2026, late evening)

Enterprise item 1: can a Metal smart account make the CFO **and** a second person (the controller) sign before a
mandate changes or a large payment leaves? Yes. MetalAccount takes several owners with weights and one threshold
(docs.metalntwx.com/build/controls/create-and-manage-a-smart-account); every call the account makes needs signatures
reaching it. `npm run four-eyes` (`src/cli/fourEyes.ts`) shows it live on Metal testnet. The full record, with
each transaction's finality certificate, is [`four-eyes.json`](four-eyes.json).

**A separate test world**, not Northwind's recorded one. Its keys are test keys (sponsor for gas, CFO, controller, a
stranger, the payee), kept outside the repo and never printed. All money is test money (*USDZ).

## What ran

Account `0x2e7df2d4dABCcfB845ED46fF140062eafAD79394`: owners the CFO's key and the controller's key, weight 1 each,
threshold 2. One agent mandate on it: 0.05 a payment, 1.00 in total, one payee.

The reverts are the account refusing the signatures, not a lack of gas. Each refused transaction was sent with the gas
its two-owner twin needed and used far less:
- step 7 used 237,568 of 614,613;
- step 8 used 45,093 of 614,613;
- step 10 used 237,722 of 595,111.

The account gives no revert reason ("unknown reason" in the simulation).

**Finality:** all 11 transactions have Metal's finality certificate stored (`data/four-eyes.sqlite`; summary in
`four-eyes.json`). Each block's header hashes to the block, and at least the quorum of validators signed. Not checked:
the BLS signature (no published testnet validator keys).

## How Purser builds it

`src/metal/fourEyes.ts` builds the account's EIP-712 `Execute` digest and the quorum signature
`abi.encode(bytes[] signers, bytes[] signatures)`, with the owners sorted by address. `test/four-eyes.test.ts` checks
that this is byte-for-byte what Metal's own `authorizeMandateCall` builds for the same call, nonce and keys. So the
account judges the signatures, not Purser's encoding. Binding uses `metal-agent mandate bind` with two `--signer-key`
flags.

## What this does not show

- **The two keys sat on one machine here.** In production each owner signs on their own device. A passkey owner
  works too, but costs about 700,000 gas per signature (metal-pay's estimate).
- **Northwind's own business account is still one owner** (the recorded run). Making it 2-of-2 is one call the
  account makes itself (`addSigners`, `setThreshold`), keeping its address, funds and mandates. Not done: it changes
  who controls the account, so it waits for Max.
- **One threshold for everything.** Metal documents no per-amount threshold. "Large" therefore means "above the
  mandate's cap": payments inside the mandate need no owner, anything else needs both.
- **A 2-of-2 has no spare key.** Losing one key freezes the account. Metal's own example is 2-of-3.

An earlier attempt in another test world (account `0xefd44854…b442`) ran the same steps with the same outcomes. Its
first runs stopped on a fee setting and a missing flag before reaching the end, so the clean record is the one above.
