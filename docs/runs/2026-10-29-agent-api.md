# Run log: an outside agent connects through the agent API (P1), 2026-10-29

These calls ran live on the rehearsal-3 world (`data/rehearsal-3.sqlite`, Airwallex sandbox). Times are UTC.

## Who connects

- `npm run outside-agent` starts a Claude agent (Sonnet 5.5) that plays Acme Research's purchasing agent. It is not
  one of ours.
- It reaches Tidemark only through the agent API: `npm run -s mcp`, an MCP server on stdio, serving it as
  `ext:acme-research`.
- It sees four tools: `request_company_card`, `company_card`, `pay_with_card` and `request_limit_raise`. It has no
  ledger, no keys and no policy.
- Its goal: "Get a company card from Tidemark for buying market reports: about 20 EUR each, at most 80 EUR a month.
  If you already have one, buy the Q4 European FX report from Contoso Reports for 19.00 EUR."

## First run (18:26)

1. `company_card`: status `NONE`.
2. `request_company_card`: "Acme Research purchasing agent", 20.00 EUR per purchase, 80.00 EUR per month, "Buying
   market research reports (about 20 EUR each), starting with the Q4 European FX report from Contoso Reports."
3. The answer: `P-0011` waits for the CFO's Face ID until 19:26.
4. The agent stopped. It said it had requested the card and would buy the report once the card is issued.

No card exists at Airwallex until Max approves `P-0011`.

## Max approves the card (18:32)

- Max approved `P-0011` with Face ID at 18:32:49. The runner then issued the card at Airwallex (audit `card.issued`).
- The card: Visa •••• 3616, 20.00 EUR per purchase and 80.00 EUR per month, as approved and read back.

## Second run: it buys, and asks for a raise (18:33)

Its goal: "Buy the Q4 European FX report from Contoso Reports for 19.00 EUR. Then buy Contoso's annual report bundle
for 45.00 EUR. If the card cannot pay something, ask Tidemark's CFO for the higher limit you need, with your reason."

1. `company_card`: ACTIVE, •••• 3616, 20.00 per purchase / 80.00 per month, nothing spent.
2. `pay_with_card` 19.00 EUR at Contoso Reports: **approved by Airwallex** (transaction `01a188f0-9977…`).
3. The agent read its limit and saw 45.00 was over 20.00, so it did not try the charge. Its `request_limit_raise`
   asked for 45.00 per purchase. It gave its reason: the bundle, and that the 80.00 a month still covers both (64.00).
4. That is `P-0012`, which waits for Max's Face ID until 19:33.
5. The agent stopped, saying it would buy the bundle once that is approved.

## Max approves the raise; a third run (18:44)

- Max approved `P-0012` with Face ID at 18:44:28. The runner pushed 45.00 per purchase to the card at Airwallex.
- The agent's goal: check the card, buy the bundle (45.00) if it allows, then try the premium data feed (30.00).
- The agent read `spent_this_month: 38.00` and left the bundle: 38 + 45 is over 80 a month.
- It bought the data feed for 30.00. Airwallex approved it.

## A bug found and fixed on the way

- The 38.00 was wrong: the 19.00 report was in the ledger twice.
  - The runner's poll saw the authorisation in Airwallex's list under its older transaction id alone, a moment
    before the list filled in the card transaction id.
  - The webhook then recorded it under the card transaction id, 0.66 seconds later by its own timestamp.
- The fix (`b144f41`):
  - The poll leaves a fresh approval listed under its older id alone for up to 2 minutes, while Airwallex fills in
    the card transaction id.
  - When both ids are known, a row under the older id is re-keyed, or merged if both were recorded.
- The restarted runner merged the live duplicate on its next poll (`card.duplicate_merged`, kept `01a188f0…`).
  The agent's spend is now 49.00 (19.00 + 30.00).
- `npm run verify`: all checks pass, including the passkey approvals of `P-0011` and `P-0012`.
