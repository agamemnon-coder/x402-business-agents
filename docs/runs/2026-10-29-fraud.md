# Invoice fraud check, 2026-10-29 (rehearsal-3 world, live Claude, no money moved)

Tier 3 item 7. `KIT11_DB=data/rehearsal-3.sqlite npm run fraud`, at about 12:04 UTC, in the world where S3 had
allowlisted Lizenzhaus Beispiel GmbH (IBAN ...3000, BIC COBADEFFXXX) and paid its November invoice.

The Airwallex rail passed in was one that throws on any call, so a blocked invoice provably reads no balance, asks
for no quote and pays nothing. Both runs: PASS.

1. **LIC-2027-01, new bank details.** Haiku classified it as an invoice; Sonnet extracted it. Code blocked it:
   `bank_details_changed`: the invoice asks for IBAN ...1000 (LT) and BIC CBVILT2XXXX; on file: IBAN ...3000 (DE)
   and BIC COBADEFFXXX. Evidence (not blocking): the invoice announces a change of bank and pushes for urgent
   payment. Opus: "do not pay", naming the classic business email compromise pattern, with seven verification
   steps. The first: call the supplier on a number already on file, never one from the invoice.
2. **LIC-2027-02, lookalike vendor** "Lizenzhaus Beispeil GmbH". Sonnet kept the misspelling. Code blocked it:
   `lookalike_vendor`, 1 letter differs from the allowlisted name. Opus: "do not pay"; it also pointed out the
   different bank account.

   After this run, code reports that difference too. A lookalike's bank details are now compared with the
   supplier it pretends to be (`bank_details_changed`, covered in `test/fraud.test.ts`). The run above predates
   that change, so its audit row lists only the lookalike signal.

No proposal was created. The audit log has two `invoice.fraud_suspected` rows with every signal, and two
`claude.read` rows for `explain_invoice_fraud`. The dashboard lists both under refusals as "Invoice blocked:
possible fraud".
