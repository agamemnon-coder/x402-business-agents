## The licence after the run (2 November, afternoon)

- **Cause, read-only:** the beneficiary was ACTIVE with SWIFT; the EUR balance was ample; no FX, so no quote; the same
  payout had been PAID five times that day (last 09:31 UTC, fee EUR 13.36); Airwallex holds no transfer for P-0005. Our
  inputs were identical, so the cause is Airwallex's sandbox fee configuration. Airwallex (Turner Vickery, Slack) calls
  this a timing issue and advises a retry with backoff; another builder measured pricing arriving 30 s to about 3.2 min
  late. Our gap: no retry, and we kept neither Airwallex's trace id nor its message.
- **Fix (in build/next before Wednesday's freeze, reviewed twice):** on `fee_unknown` and `unconfigured_client_fee` the
  payout is retried under the same request_id after 15, 30, 60, 90 and 120 s (about 5 minutes), never after the
  approval expires, re-checking holds, the payee and the EUR floor after each wait; each attempt is audited with
  Airwallex's trace and request ids. After retries, the row is closed only after a strict look-up by request_id. A
  stale row with nothing behind it can be closed with `npm run reconcile -- --close-unsent <request_id>`; before a new
  proposal, the old request_id is looked up strictly. Tests in `test/contract/airwallex.test.ts`,
  `test/close-unsent.test.ts`, `test/licence-repropose.test.ts`, `test/reconcile-strict-lookup.test.ts`.
- **12:44 UTC:** on Max's instruction ("Sluit P-0005"), the stale row was closed: Airwallex holds no transfer under
  `bc1aca54…` (strict read-only look-up). The invoice can be proposed again, with a new proposal and Max's Face ID.
