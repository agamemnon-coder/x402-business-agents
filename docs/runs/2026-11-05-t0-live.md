# T:0 live posting attempt, 2026-11-05

**Status:** T:0 bookkeeping is built; posting failed (shared key 403 CAPI71 on 3 Nov, new key 401 CAPI11 on 5 Nov), so nothing is posted.

Result: **nothing was posted.** T:0 issued a read-write key ("hackathon_read_write") for the shared "T:0 Sandbox"
entity, with permission to write journal entries there. On 5 November at 09:13–09:18 UTC, `api.t0.ai` refused that key
on its first, read-only call with `401 CAPI11` ("Missing or invalid API key; send it as Authorization: Bearer <key>").
The read-only key that worked on 3 November ([record](2026-11-03-t0-sandbox.md)) got the same 401. We checked that the
`Authorization` header reaches servers unchanged through our network. So the key or its activation needs a look on
T:0's side. This record does not claim anything is in T:0.

## What ran

- **Ledger:** a copy of the main run's ledger (`data/main-1.sqlite` of 3 November, sha256 `09895aa2…6e2e27`). The
  original was not opened for writing, and the push and sink ran on the copy.
- **Books** (`npm run books` on the copy): 190 postings, balanced in every currency.
- **Entries built offline:** we used `buildEntries` with the sandbox map (`src/config/t0Map.ts` v1) and placeholder
  account ids, because a `je_number` depends only on our postings. That gives 95 entries, all dated 2026-11-03: 3
  opening balances and 92 journal entries, with 95 distinct `PUR-` numbers. In sorted order the first is
  `PUR-009a04b037f83d390c1a6706` and the last is `PUR-ff05ee9ad116ff8f3a6d7bf2`. A `PUR-` number is a hash, so the
  numbers do not form a sequence. 90 entries are in USD, 87 of them tagged `[test USD, Metal testnet]`. 5 entries are
  in EUR. Accounts: 1200, 1201, 1210, 1590, 3000, 4000, 4100, 5000, 6100, 6350, 6800.
- **Rate:** EUR/USD 1.1179, the ECB euro reference rate for 2026-11-03 (data-api.ecb.europa.eu, series
  EXR.D.USD.EUR.SP00.A), fetched on 5 November.

## Not done, because the key was refused

- **Not posted:** all 95 entries. Posted count: 0. T:0 journal ids: none.
- **Not run:**
  - the read-back (`npm run t0 -- compare --map sandbox`, `compareOwnEntries`);
  - the totals check against the ledger;
  - the second push, which should post 0 new entries.
- **No dry run against T:0:** it needs T:0's functional currency and chart, and the API refused those calls too.

## What it showed

- **Failure safety, live:** with `T0_ENABLED=on` and a key T:0 refuses, the sink logged one line, returned without
  throwing and posted and recorded nothing. A test now covers this exact case: `test/t0-sink.test.ts`, "a key T:0
  rejects (401 CAPI11 ...)". It sits next to the test in which a payment completes while T:0 is down ("a payment
  completes even when T:0 is down; the sink only logs").
