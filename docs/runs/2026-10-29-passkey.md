# Passkey relay, 2026-10-29 (Cloudflare, live): deploy and dev tests

Tier 2 item 5. The relay Worker went live and the whole phone flow was driven in a real browser against it. These
are **dev tests by Claude**: a throwaway world, a virtual authenticator and a fake executor, so nothing real was
approved and nothing moved. The acceptance run (Max enrols on his iPhone and approves in a new world) is still to do.

## Deploy

- `npm run relay:deploy`: Worker `kit11`, wrangler 4.151.0, one SQLite Durable Object (`RelayObject`), 78 KiB
  (23 KiB gzip), startup 1 ms. Address **https://kit11.<subdomain>.workers.dev**, version `2113d66a-ea3d-4402-b7e8-98a4879ee233`.
  `RELAY_TOKEN` set from stdin (derived from the Cloudflare token; never printed).
- Free plan: SQLite Durable Objects are included; one sync every 2 s is at most 43,200 requests a day.

## Live checks from the container

1. `npm run relay -- --once` on the dev world: `/api/snapshot` serves the ledger (164 audit rows, chain intact,
   runner age 0.7 s); `/api/approvals` lists no proposal and no passkey, and carries no enrolment code hash;
   `POST /api/runner/sync` without the token answers 401. The pages carry their CSP, `nosniff`, `no-referrer`,
   `noindex` and a Permissions-Policy that allows passkeys on this origin only.
2. `npx tsx test/browser/approve.check.ts --live`: Chromium with a virtual authenticator (WebAuthn over CDP, user
   verification on) on the real `kit11.<subdomain>.workers.dev` origin, against a copy of the rehearsal-2 ledger with
   two fresh price options (P-0007, P-0008) and a fake executor:
   - enrolment with the one-time code: the runner verified the new passkey and pinned it;
   - the phone dashboard names it ("Approvals need max's passkey E_QyItYn");
   - the approval page shows both options side by side; a tap opens option B's summary; Confirm is disabled at
     first and arms after the delay; the "This is not" list names option A; the hash prefix is B's;
   - Back closed the summary and nothing was signed or approved;
   - Confirm with Face ID: the runner verified the signature, approved P-0008 as `max (passkey E_QyItYn)` and the
     executor ran once; the phone showed "Done";
   - the offline re-check (`npm run verify`) passed for that approval;
   - option A afterwards was refused by the runner ("another option, P-0008, was already approved");
   - no page errors, so no CSP violations.
3. The same check against a local relay also covers terms changed on the way: the page refused to offer them
   ("the terms do not hash to the hash shown").

Afterwards the dev world was pushed again, so the live dashboard shows it. Screenshots: `docs/approve-*.png`,
`docs/screens/dashboard-phone-passkey.png`.
