## What Visa Intelligent Commerce asks for, in its words

| Area | Visa's terms | What the docs say | Quote | Source |
|---|---|---|---|---|
| Agent identity | externalClientId/externalAppId, agentId (TRID), Visa Agent Registry Service, agent signatures, mutual TLS | The agent has Visa-provisioned ids, registers, and its signing key is checked | "validate your agent signatures and merchant encryption keys at the time of credential retrieval" | 3 |
| Payment credential | agentic token (vProvisionedTokenID), cryptogram | A token in place of the card number; each cryptogram one-time use | "Visa returns a provisioned agentic token to you"; "one-time use with a 72-hour lifespan" | 3, 1 |
| Consumer authentication | Visa Payment Passkeys, device binding, FIDO2, assuranceData | The consumer authenticates with a device-bound passkey | "Visa Payment Passkeys set up with device binding for the consumer" | 3 |
| Intent and consent | instruction, mandate | The purchase intent the consumer agreed; it cannot be edited, only cancelled and made anew | "The agreed upon purchase intent between consumer and agent"; "There is no endpoint to modify an existing instruction or mandate" | 1 |
| Spend controls | mandate parameters (declineThreshold, effectiveUntilTime, preferred merchant, restricted MCC) | The agent may only buy within the instruction's parameters | "can only request payment credentials and complete checkout within the set instruction parameters" | 2 |
| Signals | Signals, confirmation API | The agent reports each purchase's outcome to Visa | "reports that outcome to Visa via this endpoint" | 2 |
| Onboarding | TAP | Production onboarding includes TAP | "onboard to the Trusted Agent Protocol (TAP)" | 3 |

Trusted Agent Protocol (4, 5): RFC 9421 HTTP Message Signatures (Signature-Input, Signature; keyid, created, expires,
nonce; tag agent-browser-auth or agent-payer-auth), "a verifiable, cryptographic standard to help merchants
differentiate legitimate agents"; the merchant fetches the agent's public key by keyid, checks the fields, the time
window, the nonce and the signature, and blocks a request that fails.

## How our records match (and where they do not)

Visa's own words are used on /visa only where a record matches them; otherwise the page says plainly what we did.

| Visa asks for | What Purser did, in our records | Match |
|---|---|---|
| Agent identity (agent signatures) | Not in the VIC runs. The TAP run of 2 Nov (docs/runs/visa-tap-live-2026-11-02.json): the Sourcing agent's checkout signed per TAP, verified by Visa's reference proxy (commit 16d59bd); the registry was Visa's reference registry, self-hosted, with a test key: not Visa's directory, not a Visa-approved agent. | Partly, outside the entry |
| Payment credential (agentic token, one-time use) | Airi's Visa credential, which Purser binds to one purchase: vic-4 F1 (another amount) refused PURSER_CREDENTIAL_AMOUNT_MISMATCH, F2 (second use) PURSER_CREDENTIAL_ALREADY_USED, both before any Airwallex call; in vic-3 the Airi/Airwallex sandbox accepted both. Not a provisioned agentic token or a cryptogram of our own. | Our own binding, not Visa's token |
| Consumer authentication (passkeys) | Above the CFO's limit, the CFO's passkey (Face ID) signs the SHA-256 of the exact terms; vic-4 B: the same hash read back from Airi's mandate and Airwallex's PaymentIntent. A passkey of Purser's, not a Visa Payment Passkey. | Purser's passkey, not Visa's |
| Intent, consent and spend controls (instruction, mandate parameters) | The CFO's policy in Purser's code: up to EUR 20 the agent alone, at most 3 a day; above the hard cap refused (C, PURSER_ABOVE_HARD_CAP); a merchant not on the list refused (D); terms changed after the Face ID refused (E); each with 0 outside calls. Each step is written to Purser's hash-chained audit log; vic-4's record exports its 43 rows. | Purser's controls, beside Airi's mandate |
| Signals (outcome reported to Visa) | Not done: no Signals or confirmation call to Visa; outcomes are reported to Airi (airi.result_reported) and kept in our records. | Not done |

## What is not proven yet

- A Visa-provisioned agentic token or cryptogram: our runs use Airi's credential in the Airwallex sandbox.
- A real card or real money: Airi's test card, test money only.
- Agent registration with Visa (VARS) or Visa's own agent directory: TAP ran against Visa's reference registry, self-hosted.
- A Visa Payment Passkey: the passkey is Purser's (the CFO's Face ID).
- Signals to Visa.
- Production checkout: in the sandbox test runs a headless browser typed Airi's credential into Airwallex's hosted card
  page; how production works is not documented in what we could read.
