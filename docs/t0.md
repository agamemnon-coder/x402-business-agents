# T:0: Purser's books in a real general ledger

T:0 (a hackathon sponsor) is an accounting platform with a customer API. `npm run t0` posts Purser's double-entry books
(`npm run books`) to T:0 as manual journal entries, then compares T:0's P&L with our trial balance, account by account.
The code is `src/accounting/t0.ts` (client, entry builder, push, comparison) and `src/cli/t0.ts`. The tests use an
in-memory T:0 (`test/fakes/t0.ts`); see docs/runs/2026-11-03-t0-sandbox.md and docs/runs/2026-11-05-t0-live.md for what has been sent to the real API
and docs/runs/2026-11-10-t0-journal-sandbox.md for the posting of all 95 entries.

**Status:** T:0: 95 journal entries posted to T:0's shared sandbox entity on 10 Nov (first je_prod_z7kTCuZ1iiwad01q); debits equal credits, and T:0 matches our books line by line. ([record](runs/2026-11-10-t0-journal-sandbox.md)). Until then the keys were refused (403 CAPI71 on 3 Nov, 401 CAPI11 on 5 Nov). API reference: OpenAPI 1.12.1 at docs.t0.ai.

The PDFs `docs/submission/purser-deck.pdf` and `docs/submission/cheat-sheet.pdf` were printed again on 10 Nov from their sources and carry the new sentence.

```
npm run t0 -- accounts                      our chart next to T:0's: present, postable, right type
npm run t0 -- push --rate USD=0.92 --dry-run    build the entries and print them; post nothing
npm run t0 -- push --rate USD=0.92              post what T:0 does not have yet
npm run t0 -- compare --rate USD=0.92           T:0's P&L against our books; says "matches our Books line by line" only when it does
```

Without `T0_API_KEY` each command says what is missing and exits 0. The key is read from the environment only and
is never printed. `T0_ENTITY` and `T0_BASE_URL` are optional.

## What it posts

- One T:0 entry per Purser journal entry (a debit and a credit line), dated by the movement's UTC date.
- Amounts in T:0's functional currency (`amount_atoms`). When the movement was in another currency, every line also
  carries the original amount (`transaction_amount_atoms`) and the entry names its `transaction_currency`.
- Each line's memo holds the cost centre and the proof (transaction hash, clearing receipt or Airwallex id).
- `je_number` is `PUR-` plus 24 hex characters of a hash of the entry's content (opening or journal, ref, date,
  accounts, amounts), so it stays the same when Purser renumbers its entries. The `X-Idempotency-Key` is a hash of
  that id and the exact payload.
- Before posting, it lists T:0's manual entries over the same dates and skips every `je_number` already there. It
  also skips anything in the ledger's `t0_postings` table and counts a 409 CAPI34 as already posted.
- A CAPI73 (T:0 rebuilding) or a 5xx is retried once. Any other error stops the push; a re-run skips what was posted.
- An unmapped account or a missing rate stops everything before the first POST, listing every missing code or rate.

`compare` totals only entries whose `je_number` starts with `PUR-`, per T:0 account number, and sets them against our

when every mapped account agrees to the cent and the same `je_number`s are on both sides.

## The four gaps

1. **No account creation through the API.** The chart is built in T:0's app. `npm run t0 -- accounts` shows what is
   missing.
2. **No durable dedup in T:0.** Idempotency keys are refused for an hour and then forgotten, and entries have no
   external id. We dedup on our `je_number` (T:0's list) and our own `t0_postings` table. T:0 does not document
   whether `je_number` is unique.
3. **\*USDZ is posted as USD.** T:0 takes ISO codes only. The entry memo says `[test USD, Metal testnet]`, and 1210 and
   1220 hold only that test money.
4. **We do the FX.** T:0 takes no rate; it stores the ratio of the two amounts. `--rate CUR=rate` gives one rate per
   currency for every date. A daily rate source is still to do.

## What Max must do

1. In T:0, go to Connections > API Keys and create a key with `customer_api:post_journal_entries` and
   `customer_api:read`. A key's permissions cannot be changed later.
2. Create the accounts in the table above, with `account_number` = our code.
3. Set the entity's functional currency and its First Month of Books. Without the second, every post gets CAPI67.
4. Run `export T0_API_KEY=...`, then `npm run t0 -- accounts`, `push --dry-run`, `push`, and `compare`.

## Records (assumed shapes)

`src/accounting/t0Records.ts` writes Purser's suppliers, bills and payments to T:0 with `POST /v1/records`. It is built
and tested against a fake T:0 only (`test/t0-records.test.ts`). **No live write has been made.** One needs the
owner's go and call budget.

**Source of the shapes: assumed.** The OpenAPI 1.12.1 operations Purser uses (entities, gl-accounts, journal-entries,
reports) do not include `/v1/records`, and no call was made to read T:0's documentation for it. Check every shape below
against T:0's current OpenAPI before a live write; only `t0Records.ts` changes.

| What | Assumed shape |
|---|---|
| Write | `POST /v1/records`, JSON body `{ record_type, external_ref, data, approval_sha256 }`, header `X-Idempotency-Key` |
| `record_type` | `supplier`, `bill` or `payment` |
| `data`, supplier | `{ name }` |
| `data`, bill | `{ supplier, number, issue_date, due_date, currency, total, document_sha256 }` (amounts as two-decimal strings) |
| `data`, payment | `{ supplier, bill_number, date, currency, amount, rail_ref }` |
| Answer | `200` with `{ id, record_type, external_ref }`; `409` for a repeated idempotency key; `429` with `Retry-After` |
| Look-up | `GET /v1/records?external_ref=...`, answer `{ data: [{ id, record_type, external_ref }] }` |

What holds, whatever T:0's real shapes turn out to be:

- **Approval.** A batch is written only when an approved proposal of kind `t0_records` names the batch's hash (the
  SHA-256 of its records' keys) and its stored terms still hash to the signed hash. Every request carries that hash.
  Without it the client refuses and sends nothing.
- **Once per record.** A record's key is the SHA-256 of its content. It is the idempotency key, and the ledger's
  `t0_records` table keeps what was written, so a re-run makes 0 writes.
- **Retries.** A `429` waits and sends again with the same key. A lost answer (a dropped connection, a timeout, a 5xx)
  is resolved by looking the record up by `external_ref` before any second write. A `409` is taken as written when the
  record is found.
