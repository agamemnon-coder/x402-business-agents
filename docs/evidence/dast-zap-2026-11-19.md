# DAST: OWASP ZAP baseline scan of the two test sites

Run on 2026-11-19 (15:32 to 15:37 UTC) with OWASP ZAP 2.17.0's own `zap-baseline.py`, once per site, against our own
public test sites only: the relay Worker, https://kit11.max-31b.workers.dev, and the hosted /try,
https://purser-try.max-31b.workers.dev. Test money only; no partner system was scanned. **0 High, 0 Medium**; 5 Low and
9 Informational alert types over the two sites, all accepted below with the reason. Nothing needed a fix.

The same scan now runs weekly and on demand in CI ([dast-zap.yml](../../.github/workflows/dast-zap.yml)), in ZAP's image
pinned by digest; it keeps the reports as an artifact and fails only on a High-risk alert.

## How it was run

The baseline is passive: ZAP's spider walks the site for at most one minute, then ZAP's passive rules read every
response. It sends no attack payloads.

The Docker daemon was not running on the machine this was run from (and its disk had about 3 GB free, too little for
ZAP's image), so the image was not used. Instead, what the image contains was set up by hand, the way its Dockerfile
(`docker/Dockerfile-stable` at tag v2.17.0) builds it:

1. ZAP 2.17.0 for Linux (`ZAP_2.17.0_Linux.tar.gz`), SHA-256 checked against ZAP's own `ZapVersions.xml`
   (`efe799aa…ddde5a`: OK), unpacked as `/zap`.
2. The add-ons updated as the image build does (`zap.sh -cmd -silent -addonupdate`) and copied into `/zap/plugin`.
3. `zap-baseline.py` and `zap_common.py` from ZAP's repository at tag v2.17.0, unchanged, in `/zap`, run with the
   image's `IS_CONTAINERIZED=true` and reports in `/zap/wrk`. The image's `zap-x.sh` starts Xvfb and then `zap.sh`; a
   stand-in that runs `zap.sh` only was used (the scan runs ZAP headless with `-cmd`). Java: OpenJDK 21. Python client:
   `zaproxy` 0.6.0 from PyPI.
4. ZAP's own connections went through the machine's HTTPS proxy (`-z` with ZAP's `network.connection.httpProxy`
   options). That option is not needed, and not set, in CI.

Command, per site (`<site>` is `kit11` or `purser-try`):

```sh
IS_CONTAINERIZED=true /zap/zap-baseline.py -t https://<site>.max-31b.workers.dev -I \
  -J zap-<site>.json -r zap-<site>.html -w zap-<site>.md \
  -z "-config network.connection.httpProxy.enabled=true -config network.connection.httpProxy.host=127.0.0.1 -config network.connection.httpProxy.port=<local proxy port>"
```

`zap-baseline.py` used ZAP's Automation Framework (its default inside the image): a one-minute spider, then
`passiveScan-wait`, then the reports. `-I` keeps warnings from failing the exit code, as in CI, where the job then
fails on any High-risk alert in the JSON report.

## Results

| Site | URLs found by the spider | Rules passed | Warnings | High | Medium | Low | Informational | Exit code |
|---|---|---|---|---|---|---|---|---|
| https://kit11.max-31b.workers.dev | 172 | 61 | 7 | 0 | 0 | 3 | 5 | 0 |
| https://purser-try.max-31b.workers.dev | 10 | 64 | 4 | 0 | 0 | 2 | 4 | 0 |

ZAP's "Warnings" count rules; High to Informational count alert types by risk (one rule, 90004, raises two alert
types). purser-try's spider found 10 URLs: /try draws its screens with JavaScript, which the baseline's spider does not
run (ZAP says so itself with 10109 on kit11). The browser checks in CI cover those screens.

## Findings and what was done

| Risk | Rule | Alert | Where | Decision |
|---|---|---|---|---|
| Low | 90004 | Cross-Origin-Embedder-Policy header missing | both sites, 5 + 3 pages | **Accepted.** COEP only matters for cross-origin isolation (SharedArrayBuffer, precise timers), which no page uses. Every page already sends `Cross-Origin-Opener-Policy: same-origin` and a CSP that loads nothing from another origin (`default-src 'none'`, `img-src 'self'`). |
| Low | 90004 | Cross-Origin-Resource-Policy header missing | both sites, 5 + 5 responses | **Accepted.** CORP stops other sites from loading our responses as subresources. Every response it was raised on is public and the same for every visitor (the pages, `robots.txt`, a logo); none carries a session or a secret. The relay's one cookie (its API session, `worker/src/core.ts`) is `SameSite=Strict`, `HttpOnly`, `Secure`, path `/api`; Purser Cloud sets none. A candidate for a later hardening pass (`same-site` on the pages), not a vulnerability. |
| Low | 10063 | Permissions-Policy header not set | kit11, `/assets/approve.js` only | **Accepted (not applicable).** Permissions-Policy governs documents, and every HTML page sends it (checked with curl on `/`: `publickey-credentials-get=(self), …, usb=()`). A script file is not a document; the project's own header rules hold assets to a different set (`test/security-headers.rules.ts`). |
| Info | 10027 | Information disclosure: suspicious comments | both sites, 15 + 10 | **Accepted.** ZAP matches words (FROM, WHERE, QUERY, USER, LATER, ADMIN) in comments of the inline scripts. Every instance was read: explanatory comments, no secret, key, credential, internal host or to-do. The one with ADMIN (purser-try) says the operator's platform admin token is kept in that page's memory only; no token is in the page. |
| Info | 10031 | User controllable HTML element attribute (potential XSS) | kit11, `/lab?run=all` | **False positive.** The value `all` matches a fixed `id="all"` on the "Run all again" link. A probe (`/lab?run=zq9x"><b>`, sent with curl) does not appear anywhere in the response: the parameter is not reflected. |
| Info | 10049 | Non-storable content; storable and cacheable content | both sites | **Accepted, by design.** Pages are `cache-control: no-store` (an approval page must never come from a cache); static assets (logo, favicon, font) are cacheable for a day. |
| Info | 10015 | Re-examine cache-control directives | both sites | **Accepted, by design**: the same `no-store`. |
| Info | 10109 | Modern web application | kit11 (`/film`, `/policy`) | **Informational**: the pages run JavaScript, so a spider that does not run it sees less (see above). |

Nothing found was in the money path (approval, signature, payment) and nothing was Medium or above, so nothing was
changed for this scan.
