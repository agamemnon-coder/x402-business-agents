# Regression tests with bug fixes (evidence, 19 November 2026)

For the OpenSSF Best Practices criterion `regression_tests_added50`: regression tests are added for at least half of the
bugs fixed in the last six months. The project's first pull request was merged on 2 November 2026, so the six months
are the project's whole life.

## How this was measured

From GitHub's API on 19 November 2026: every merged pull request (398), of which **46 have a title that names a fix**
(the words fix, bug, flaky, wrong, regress, broken, crash or race). For each, the files it changed under `test/`.

| Measure | Count |
|---|---|
| Merged pull requests whose title names a fix | 46 |
| … that changed or added at least one test file | **43 (93%)** |
| … that added a new test file | 20 (43%) |
| … with no test change | 3: #357 (wording and an empty state), #135 (a gitleaks allowance, no code), #4 (a merge of another branch) |

Limits of the measure, stated plainly: a pull request's title is not a bug tracker (bugs here were mostly found in
reviews and fixed in the same pull request, not filed as issues); one pull request often fixes several things and adds
features too; and a changed test file shows that the fix was tested, not that every single bug in it got its own
failing-first test. Where a pull request fixed security findings, its tests say so per finding: for example
`test/cloud-security.test.ts` ("each test is one attack that worked before the fix"), `test/security-sweep-*.test.ts`,
`test/cloud-passkey-remove-race.test.ts` (#270) and `test/security-txt.test.ts` (#285). Since 19 November the test
policy in [CONTRIBUTING.md](../../CONTRIBUTING.md#tests-come-with-the-change) asks for a regression test with every fix.
