# Stream: zero-trust

Branch: `zero-trust-1112` (base origin/platform). Pull request base: main.

## Context

ZERO TRUST, PROVEN LAYER BY LAYER. Purser's promise, which the hackathon's host publicly liked: a spending limit in a prompt can be talked out of, so the limit is enforced outside the model, in layers that do not trust each other. The owner wants this made explicit and tested as zero trust: for every attack, assume the earlier layers are already compromised and prove that the next independent layer still stops the money. The layers, from the inside out: L1 the Claude agent (may be wrong, manipulated or fully hostile); L2 Purser's deterministic code (invoice and fraud checks, the CFO policy: acting-alone limits, cash floors, payee rules, velocity, the policy engine in src/policy/*); L3 the CFO's passkey signature over the exact terms (terms hash, single use, expiry; src/passkey/*, src/lib/terms.ts, the relay and phone pages); L4 four eyes above the CFO threshold (src/policy/fourEyes.ts); L5 the rails' own controls that Purser does not own: Airwallex card controls per agent, Airwallex's transfer approval workflow, and the on-chain Metal mandate per agent (cap, budget, payee, expiry); L6 the record: hash-chained audit log and ledger with verify and reconcile, plus pause per agent and the emergency stop. Around them: tenant isolation in Purser Cloud (cloud/src/*), webhook signature checks, agent principals and keys (src/policy/principals.ts). Much of this is already tested in scattered places (src/redteam/*, test/adversarial.test.ts, test/try-sign.test.ts, the chaos tests, test/policy-rules.test.ts, the cloud red-team tests test/rt4-cloud-*.test.ts, docs/security.md, docs/controls-matrix.md, docs/threat-model*). Your job is to turn it into ONE explicit, executable zero-trust matrix that drives the real code, find the cells nothing tests, fill them, fix any real hole, and generate an honest report. No network calls. Do not change site pages (another stream builds /security; it will read your report later), README.md or llms.txt. Read the scratchpad maps platform-engine.json and agents-and-cost.json (answers 2, 3, 6) and docs/security.md and docs/controls-matrix.md before reading code. Live evidence may be CITED only from existing run records under docs/runs (for example the card decline LIMIT_EXCEEDED of 7 Nov, the on-chain refusal mandate_cap_exceeded, the transfer held IN_APPROVAL by Airwallex's own workflow on 10 Nov); never claim a live proof that has no record.

## Task 1: model-and-matrix (the zero-trust model as data and the executable matrix on the real code)

- src/zerotrust/model.ts: the layers above as data (id, name, who owns it: the model, Purser's code, the CFO's device, a second person, the rail, the record) and a list of ATTACKS as data. Each attack has: an id, a plain one-sentence description, the breach set (which components the attacker is assumed to control: the agent's output, the invoice or e-mail content, an agent's API key, the hosted relay Worker, the phone page, a signed approval in transit, Purser's own decision code, the database file, a webhook sender, another tenant's session), the money action it tries, the layers it thereby bypasses, the layer expected to stop it, and optional live evidence (a path under docs/runs plus the fact it shows).
- test/zero-trust.test.ts: one test per attack that DRIVES THE REAL CODE with the breached components replaced by hostile stand-ins (an agent that always answers pay with any payee and amount; decision code forced to say pay; a relay that alters terms or replays an assertion; edited database rows; a forged webhook; a stolen key), and asserts three things: no money moved (no executed payment, card charge or on-chain payment in the ledger or in the stand-in rails), the attempt was stopped by a layer that is NOT in the breach set, and the stop left a record (an audit row or refusal with a reason). The stand-in rails must refuse exactly as the live rails did in the cited run records (card limit, merchant category, mandate cap and payee, transfer approval hold); say where each stand-in gets that behaviour.
- Cover at least these attacks, reusing existing harnesses where they exist: a hostile agent on each money path (card purchase, bank payout, on-chain payment, supplier invoice); prompt injection in an invoice and in an e-mail; a changed amount, payee or currency after the CFO signed, tried at payment, at booking and at the archive (the same hash must refuse or flag it at each stage); replay of a used approval; an expired approval; an approval for another proposal or another company; a signature by a passkey that is not enrolled or was revoked; one person approving twice where four eyes is required; loosening the policy without a signature; a stolen agent key used above its mandate; Purser's own decision code compromised so it tries to execute without a signature or above a card limit or mandate (the rail stops it); the relay Worker compromised (altered terms shown or forwarded; a forged assertion); a forged or replayed Airwallex webhook; database rows edited after the fact (the hash chain and verify detect it); cross-tenant read and write in Purser Cloud; a paused agent or the emergency stop being ignored by a later request.
- A property test: for random combinations of breached inner layers and random attacks from the list, the outcome is never money moved unless the breach set includes every layer that guards that money path; from it compute for each money path its DEPTH: the smallest number of independent layers that must all fail before money moves.
- Every attack id appears exactly once in the model and in the test; a test fails if a model entry has no test or the other way round.

## Task 2: gaps-and-fixes (find untested cells and real holes, fix them)

- Build the coverage view: money paths (rows) against layers (columns); each cell says which attack ids prove that layer stops that path when the inner layers are breached. List the empty cells that SHOULD be coverable (a layer that claims to guard a path but has no test with the inner layers breached) and write those tests.
- Attack it yourself: for each money path, spend real effort trying to move money in the test harness with the inner layers breached (think like an attacker who has read the code: race conditions between approval and execution, a second execution of the same approval, terms canonicalisation tricks such as different number formats, Unicode look-alikes or key order, an approval reused across rails, time and expiry edges, partial failures and retries, state restored from a backup). Every successful or near-successful attempt becomes a test. A real hole is fixed with the smallest change (test first) if it is inside Purser's code; if it cannot be fixed in scope, it is documented as an open risk, never hidden.
- If, after merging the trunks, the AP agent cores exist (src/ap/checkerCore.ts and src/ap/payerCore.ts from another stream), add attacks for them (a hostile Checker and a hostile Payer); if they do not exist yet, add model entries marked pending with no test and exclude them from every count.

## Task 3: report-and-ci (generated report, command, CI)

- npm run zero-trust: runs the matrix and writes docs/zero-trust/report.json and docs/zero-trust.md, both generated only from the model and the test results (never typed): the layers; the table of attacks with breach set, bypassed layers, the layer that stopped it and its evidence (the test name, plus the live run record when one is cited); the coverage view; the depth per money path; the open risks; the date and commit. The numbers a page may quote later (attacks run, attacks stopped, layers, minimum depth) are top-level fields of the JSON.
- A test asserts the committed report equals what the command generates (so it cannot drift) and that every cited run record exists and contains the cited fact.
- Add the matrix to CI (it runs with the normal suite; no network) and to the coverage areas if the repository's coverage check lists areas.
- docs/security.md and docs/controls-matrix.md get one short section each that points to the generated report instead of repeating it; fix statements there that the matrix shows to be inaccurate.
- Plain English throughout; a CFO must be able to read docs/zero-trust.md top to bottom in two minutes: the first screen is the principle in two sentences and the table of layers; details fold below.

## Review lenses

- **attacker**: You are a red-team engineer. Your goal is to move money in the test harness, or to make the matrix claim more than it proves. Read the model and the tests, then attack: find an attack the list misses; find a test that passes for the wrong reason (the stand-in refuses regardless of input, the breached layer was not really breached, the assertion checks a flag instead of the ledger and the rails); find a stopping layer that secretly depends on a breached one; try canonicalisation, replay, race, retry, restore-from-backup and cross-rail reuse tricks against the approval and execution code. Write each successful finding as a concrete failing scenario with the code path. A real hole in the product is a blocker.
- **honesty**: The report and docs say only what the tests and the cited run records prove. Stand-in rails are named as stand-ins and their behaviour is tied to a live record; nothing implies the live rails were attacked in this stream. Depth numbers follow from the model and tests. Pending rows are excluded from counts. Open risks are stated plainly. docs/security.md and docs/controls-matrix.md agree with the report. No site page, README.md or llms.txt changed. The report is readable by a CFO: check the first screen.
- **correctness**: The matrix drives the real production code paths (not copies), the model and tests stay in lockstep, the property test is meaningful and not vacuous, the generated report is deterministic and the drift test works, CI includes the matrix, existing tests are untouched or stronger, and the run time of the new tests is reasonable (report it).
