# Stream: icc-ready (Visa Intelligent Commerce Connect, ready to run the hour access arrives)

Branch: `icc-ready-1112` (from origin/platform). Pull request base: main.

## Context

For the hackathon's Visa award only two things count as Visa tooling: Visa Intelligent Commerce (VIC) and Intelligent Commerce Connect (ICC), Visa Acceptance's (Cybersource's) developer path to Visa Intelligent Commerce. Purser already ran VIC through Airwallex's Airi on 7 November (src/airi/*, docs/runs/2026-11-07-vic-1.md). A jury of seven scored the Visa part lowest and said what would change that: a direct Visa integration beside Airi, in which the CFO's signed limits become the Visa-side instruction.

On 12 November the owner signed up for the "Intelligent Commerce Sandbox" at https://developer.cybersource.com/hello-world/agentic-sandbox.html (organisation id chosen: `purser_sandbox`). Access is NOT granted yet (no e-mail so far). Your job: prepare everything so that the live sandbox run takes under an hour once credentials arrive, without claiming anything that has not run.

Purser's principle, which the integration must show: an AI agent may only buy within limits the CFO signed with a passkey over the exact terms. The Visa-side instruction (amount cap, merchant, expiry, the agent it is for) is derived from those signed terms, carries the terms hash where the API offers a free-text or reference field, is read back and compared before any credential is requested, and the purchase is refused when anything differs.

## Hard rules for this stream

- Research first, from primary sources only: the public documentation on developer.cybersource.com, support.visaacceptance.com and developer.visa.com about the Intelligent Commerce / agentic commerce APIs (enrol a card, create a purchase instruction or mandate with constraints, retrieve a payment credential, confirm or report the transaction result, authentication). You may fetch those pages (at most 40 fetches). Write what you found, with the URL of every fact, in docs/visa-icc.md. Cite nothing you could not verify; where the public documentation is silent, write "unknown until sandbox access".
- NO calls to any Visa or Cybersource API in this stream: there are no credentials. No other external calls.
- No emulator that poses as Visa: a stand-in server exists only under test/ and is named and labelled a test stand-in built from the documented request and response shapes. Nothing on the site, in the README or in docs may say or imply that ICC ran. The only public status sentence allowed is: "Intelligent Commerce Connect: access requested, not granted yet; not used in this entry."
- Card data: only the sandbox's documented test card; never a real card; a credential is single-use, never logged, never given to a model, removed after use; a test proves no card number or CVV pattern reaches logs, run records or the ledger (see how src/airi handles this and reuse it).
- Secrets only from the environment (document the NAMES; the owner sets the values later); never print them. If the API uses HTTP signature or JWT authentication, the signing code is tested against the documentation's own worked example if it publishes one.

## Tasks

1. research-and-design. docs/visa-icc.md: the API as documented (endpoints, authentication, the objects and their fields, the constraint fields an instruction supports, how a credential is retrieved and what it contains, how the result is reported, sandbox test data), each fact with its URL and the date read; then the mapping from Purser's signed approval terms (see src/lib/terms.ts and the Airi mapping in src/airi/purchase.ts and src/airi/policy.ts) to the ICC instruction; what Purser checks on read-back; what is unknown until access; and a call estimate per run.
2. client-and-flow. src/icc/*: a small client for the documented endpoints behind an endpoint allowlist, with a call budget and call log in the repository's style (src/airwallex/callBudget.ts), timeouts, and idempotency keys where the API supports them; the flow: from an approved proposal (the CFO's passkey over the exact terms) build the instruction, create it, read it back, compare it with the signed terms and refuse on any difference, request the single-use credential, hand it to the same checkout step the Airi rail uses if that fits (src/airi/hostedCheckout.ts) or stop before checkout if the documentation does not allow it, report the result, and write audit rows with origin data like the other rails. A rail entry `icc` behind a flag that is off by default (KIT11_ICC_RAIL=on), so nothing changes for existing runs. Tests first, against the labelled test stand-in: the happy path; a changed amount, merchant or expiry on read-back is refused; an expired or over-cap instruction is refused before a credential is requested; a lost answer is not sent twice; no card data in logs, records or the ledger.
3. cli-runbook-record. `npm run icc -- preflight | run | record`, guarded like the other live commands (a go variable, a call budget, a call log, a world of its own): preflight makes no purchase and at most two read calls; run does one under-limit purchase and one over-limit attempt that must be refused; record writes docs/runs/<date>-icc.md and .json from the audit rows and the call log only. A one-page runbook docs/runs/driver/icc-runbook.md: what the owner must do in the Cybersource Business Center when access arrives (create the API key, which values go into which environment variable NAMES), the commands in order, the expected output, the call estimate, what to do when a step fails.
4. page-hook. A small renderer in a new file (for example src/redesign/iccBlock.ts) that returns the ICC block for /visa ONLY when a run record JSON exists under docs/runs, reading every number and id from it; with no record it returns the one allowed status sentence. Wire it into /visa with the smallest possible change (another stream is rewriting /visa at the same time: one import and one call, nothing else), with tests for both states. Do not touch other pages, the README or llms.txt.

## Review lenses

- **correctness-and-safety**: the client matches the documented API (check each request against the cited documentation), the read-back comparison cannot be bypassed, nothing is sent twice, the budget counts before sending, the flag-off path changes nothing, card data never reaches logs, records, the ledger or a model.
- **honesty-and-design**: docs/visa-icc.md cites a URL for every fact and marks unknowns; nothing anywhere says or implies ICC ran or that Visa approved anything; the stand-in is under test/ and labelled; the /visa hook shows only the allowed sentence until a record exists; the page stays calm in both states.
