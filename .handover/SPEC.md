# Stream: faceid-onchain-prep

Branch: `faceid-onchain-1112` (base origin/main). Pull request base: main.

## Context

FACE ID ON CHAIN: make the live run safe to do today. Today the owner signs on the Metal testnet with the real Face ID of an iPhone: the phone's passkey becomes one of two owners of a small on-chain account (ERC-7913, OpenZeppelin WebAuthn verifier, P-256 precompile) and signs a mandate action. The path exists on main (npm run owners -- setup | propose | status; proposal kind owners_execute; flag KIT11_PASSKEY_OWNERS=on; src/cli/ownersExecute.ts, src/metal/ownersExecute.ts, src/executors/ownersExecute.ts, src/metal/passkeyRelay.ts, src/metal/passkeyOwner.ts). It ran on 1 Nov with software stand-in passkeys (npm run passkey-owners, docs/runs/passkey-owners.json) and once in a dry run with Chrome virtual authenticators; no real phone has signed on chain yet. A read-only map of this path with file names, gaps, call counts and risks is in the scratchpad maps file metal-live.json: read its answers 1, 2, 3, 6 and 8, its risks and its open_questions before reading code. Your job is to close the gaps so the orchestrator can do the live run with the owner in one sitting inside a strict call budget. You make NO network calls in this stream: no JSON-RPC, no faucet, no relay, no deploy. Do not change site pages, README, llms.txt or docs/claims.md: claims follow after the live run. The planned live run, so you know what to build for: (1) owners preflight; (2) the owner enrols the iPhone passkey on the hosted relay; (3) a second approver is enrolled (a second real device, or a labelled virtual test-controller); (4) owners setup creates and funds the small 2-of-2 account; (5) propose: bind a Sourcing mandate (cap 0.05, budget 0.50, Stockline only), the owner signs with Face ID, the second approver signs, the runner relays executeSigned; (6) the Sourcing agent pays 0.05 inside the mandate and one payment over the cap is refused on chain; (7) propose-revoke, both sign, the mandate is revoked; (8) owners record writes the run record.

## Task 1: budget-and-fresh-world (guard, call budget, self-contained world, donor funding, preflight, revoke, pay, error decoding)

a) Guard and budget. Every owners command that touches the network (setup, propose if it does, status, the new commands below) and the runner's execution of an owners_execute proposal refuse to run unless OWNERS_GO=yes, OWNERS_CALL_BUDGET (a whole number, cumulative for this world across commands and processes) and OWNERS_CALL_LOG (a JSONL file path) are set, in the style of the existing guards (see src/metal/hold.ts budgetedTransport, the tokenize guards on origin/tokenize-1110 src/tokenize/client.ts if you want a second example via git show, and src/airwallex/callBudget.ts). Every JSON-RPC request on this path (reads through the public client, sends, receipt polls) is appended to the log BEFORE it is sent ({at, method, step, pid}); the request that would exceed the budget is not sent and fails with a clear error. Calls made inside the pinned metal-agent CLI cannot be counted per request: log each CLI invocation as one line labelled cli:<command> and say so in the record. The runner (npm run relay) must apply the same budget when it executes an approved owners_execute proposal.
b) Self-contained world. Today npm run owners -- propose throws 'no business account in the ledger; run npm run bootstrap' because it calls addresses(db). Make the owners flow work in a fresh world without npm run bootstrap: whatever it needs from a bootstrapped world (the Sourcing agent's key and address, the payee address for the mandate) is created by owners setup itself in the minimal way (new key files under KIT11_KEYS_DIR, which must be outside the repository; no on-chain transaction beyond what the flow itself needs). A bootstrapped world must keep working.
c) Donor funding. Allow funding the gas sponsor and the new account from a named existing key file: OWNERS_DONOR_KEY (a path) gives one counted transfer each. If it is unset the existing behaviour (faucet or KIT11_RECYCLE) stays.
d) npm run owners -- preflight: no transactions and at most 3 read calls (chain id, donor balance, verifier bytecode present), all counted. It prints the plan: each step, the expected transactions, the estimated calls per step and in total, and what the owner does on the phone at each step. It refuses when the relay URL or token configuration is missing or the keys directory is inside the repository.
e) npm run owners -- propose-revoke: builds the revoke proposal for the mandate this world bound (checkOwnersTerms already allows a revoke; the CLI only builds a bind today).
f) npm run owners -- pay: the Sourcing agent pays 0.05 inside the bound mandate to the payee, then attempts one payment above the per-payment cap, which must be refused on chain; both outcomes are written to the audit log with their transaction hashes or the refusal reason. Reuse what the 1 Nov script (src/cli/passkeyOwners.ts) does by extracting shared helpers; do not copy logic.
g) Decode the account's custom errors when a transaction reverts, instead of 'unknown reason'.
h) Nothing is sent twice: every send on this path records its hash before or as it is sent, and a re-run after a crash between send and receipt continues from the recorded hash. Cover it with tests.
Tests for each item, with the in-process stand-ins the existing tests use (test/owners-execute.test.ts, test/passkey-owner.test.ts).

## Task 2: second-approver-record-rehearsal (second approver, run-record writer, rehearsal test, runbook)

a) Second approver. The account needs two different approvers. Support both ways and document them: (i) a second real device enrolled with the existing npm run passkey -- add <name>; (ii) a labelled virtual approver for when the owner has only one device: a driver script docs/runs/driver/test-controller.ts with the commands enrol and approve <proposal id>, built on the Chromium virtual-authenticator helpers in docs/runs/driver/thursday-dry.ts (functions phone, enrol, sign), that works against the HOSTED relay (its URL from the environment, as the runner prints it), keeps the virtual authenticator's credential in a file under KIT11_KEYS_DIR between invocations (mode 600, never in the repository), refuses any name other than test-controller, and is labelled as virtual in its output, in the audit rows it leads to (where the existing code allows a label) and in the run record. It must never be able to stand in for the owner's own approval.
b) Run-record writer. npm run owners -- record writes docs/runs/<date>-faceid-onchain.json and a readable .md next to it, built only from the world's audit rows (owners.account_created, owners.sent, owners.executed, the pay and refusal rows, the passkey enrolment rows) and the call log: network and chain id, verifier address and artifact, account, threshold, the owners (passkey fingerprint and label; a device description taken from OWNERS_DEVICE_CFO and OWNERS_DEVICE_CONTROLLER and recorded as 'as stated by the owner', because attestation is none and the device type cannot be proven), each step with outcome, transaction hash and explorer link, proposal ids, terms_sha256 and the on-chain digest, calls used by method against the budget, and a deviations list read from an optional text file. Dates come from the audit rows. It makes no network calls. Follow the shape of docs/runs/passkey-owners.json where it fits.
c) Rehearsal test. One automated test drives the whole planned run (preflight, setup with donor funding, bind proposal, two approvals, execute, pay inside the mandate, over-cap payment refused, revoke proposal, two approvals, execute, record) against in-process stand-ins and asserts: the call log counts match what was sent; the budget stops the run at the right request; a simulated crash between a send and its receipt does not lead to a second send; an expired proposal (15 minutes) is refused and a fresh one works; the record equals what the audit rows say.
d) Runbook. docs/runs/driver/faceid-onchain-runbook.md, one page: the exact commands in order with the environment variable NAMES they need (no values), the expected output line after each, what the owner does on the phone at each step and what the screen shows, the call estimate per step, and what to do when a proposal expires, a signature is refused or a transaction reverts.
e) Check the phone approval page for owners_execute (src/approve/client.ts) in the existing browser check at 390 px: the owner must see the account, what is bound or revoked, the per-payment cap, the budget, the payee, the digest and the expiry before the Face ID button. Fix only real defects; no redesign.

## Review lenses

- **correctness**: Does the code do what the spec says, and are the tests meaningful (would they fail if the behaviour broke)? Hunt for: any path that can send a transaction twice; budget counting that misses a request or counts after sending; the runner executing owners_execute outside the budget; a fresh world that still needs bootstrap; propose-revoke terms that the on-chain account would reject; wrong EIP-712 digest or deadline handling; resume after a crash; regressions for bootstrapped worlds and for the 1 Nov script.
- **security**: Keys and trust. No private key, RPC URL, relay token or secret can reach logs, the call log, the run record, output or git. Key files are created with mode 600 outside the repository and the code refuses a keys directory inside it. The virtual test-controller can never approve as the owner, cannot be renamed, and is labelled everywhere. Donor funding cannot be pointed at an arbitrary address by a malformed environment. The guard cannot be bypassed by calling an inner function from another CLI. Review what a compromised relay page could make the phone sign and whether the page shows the owner enough to notice (docs/security.md has the accepted risk; do not widen it).
- **honesty**: The run record and runbook say only what the audit rows and call log prove. The device description is recorded as stated by the owner, not as proven. A virtual second approver is labelled as virtual in the record. Nothing in the site, README, llms.txt or docs/claims.md changed. No claim that a real phone has signed on chain appears anywhere before the live run. The runbook's call estimates match what the code will send.
